> JYP-Word는 매일 아침 정해진 분량의 영단어를 예문과 함께 학습하는 습관에서 아이디어를 얻어 만든 개인 영어 단어 학습 프로젝트입니다.
>
> 단어, 뜻, 발음, 예문, 예문 해석을 미리 정제된 데이터로 준비하고, 사용자는 자신의 수준과 관심 분야에 맞는 단어를 매일 20개씩 학습하는 것을 목표로 합니다.

## 이 프로젝트에서 확인하려는 것

```text
정제된 단어 데이터 ──▶ 개인별 단어 선정 ──▶ 매일 20단어 학습 ──▶ 학습 상태 누적
```

이 프로젝트는 단순히 랜덤 영단어를 보여주는 데서 그치지 않고, 다음 질문에 답하는 것을 목표로 합니다.

- 매일 새로운 20단어를 어떻게 안정적으로 선정할 것인가?
- 회원가입 없이도 사용자별 학습 상태를 어떻게 유지할 것인가?
- 사용자가 늘어나더라도 불필요한 학습 이력을 과도하게 저장하지 않으려면 어떻게 설계해야 하는가?
- 단순 랜덤 학습에서 복습, 난이도 조절, 학습 이력 기반 추천으로 어떻게 확장할 것인가?

## 학습 데이터 구성

영단어 데이터는 사용자가 학습할 때마다 LLM이나 외부 사전 API에서 생성하지 않습니다.

서비스 실행 전에 다음 정보를 미리 준비하고 검수한 뒤 정적 데이터 또는 DB에 저장하는 방식을 기본으로 합니다.

| 데이터 | 설명 |
| --- | --- |
| 단어 | 학습 대상 영단어 |
| 발음 | 단어의 발음 정보 |
| 뜻 | 한국어 의미 |
| 품사 | 명사, 동사, 형용사 등 |
| 예문 | 단어의 의미를 이해할 수 있는 영어 문장 |
| 예문 해석 | 예문의 한국어 해석 |
| 난이도 | 초급, 중급, 고급 등 |
| 카테고리 | 회화, 공학, 비즈니스, IT 등 관심 분야 |

난이도와 카테고리는 서로 다른 개념으로 관리합니다.

```text
Difficulty
├── BEGINNER
├── INTERMEDIATE
└── ADVANCED

Category
├── GENERAL
├── CONVERSATION
├── ENGINEERING
├── BUSINESS
└── IT
```

하나의 단어가 여러 카테고리에 포함될 수 있으므로 장기적으로는 `Word`와 `Category`를 다대다 관계로 구성할 수 있습니다.

## 단어 데이터 관리 방향

초기 단어 데이터는 CSV, JSON 등의 파일 형태로 관리하고 서비스에서 사용할 수 있도록 DB에 적재하는 방식을 고려합니다.

```text
data/
└── words.csv
       │
       │ import
       ▼
┌───────────────────────┐
│ Word                  │
│ Meaning               │
│ Example               │
│ Category              │
│ WordCategory          │
└───────────────────────┘
```

런타임에서는 외부 API나 LLM을 호출해 학습 콘텐츠를 생성하지 않고 이미 준비된 데이터를 조회합니다.

이를 통해 다음을 얻을 수 있습니다.

- 같은 단어의 뜻과 예문이 사용자마다 달라지지 않음
- 외부 API 및 LLM 비용 제거
- 학습 데이터 품질 사전 검수 가능
- 외부 서비스 장애와 무관한 안정적인 제공
- 데이터 변경 이력을 별도로 관리 가능

## 하루 20단어 선정

사용자는 선택한 난이도와 카테고리에서 하루 20개의 단어를 학습합니다.

단순히 매 요청마다 랜덤 20개를 반환하면 새로고침할 때마다 다른 단어가 나타날 수 있으므로, 같은 사용자와 같은 날짜에는 동일한 학습 세트가 만들어져야 합니다.

장기적으로는 다음과 같은 결정적 랜덤 방식을 고려합니다.

```text
사용자 식별값
+ 날짜
+ 난이도
+ 카테고리
      │
      ▼
     Hash
      │
      ▼
Deterministic Seed
      │
      ▼
오늘의 20단어
```

같은 입력에서는 항상 같은 결과가 나오도록 만들어, 오늘의 20단어 자체를 매번 20개의 Row로 영구 저장하지 않는 방향을 고려합니다.

## 초기 사용자 데이터 관리

초기 버전에서는 회원가입과 로그인 기능을 두지 않습니다.

사용자의 학습 상태는 브라우저의 `IndexedDB`에 저장하는 Local-First 방식을 사용합니다.

```text
Spring Boot
└── 단어 데이터 제공

React
└── IndexedDB
    ├── Settings
    ├── DailyStudy
    ├── WordProgress
    └── ReviewQueue
```

저장할 수 있는 정보의 예시는 다음과 같습니다.

```text
WordProgress
├── wordId
├── status
├── correctCount
├── wrongCount
├── firstStudiedAt
├── lastStudiedAt
└── nextReviewAt
```

이 구조에서는 Spring Boot 서버가 사용자의 존재를 알 필요가 없습니다.

단, IndexedDB는 브라우저 Origin 단위 저장소이므로 다른 기기나 다른 브라우저에서는 학습 상태가 자동으로 공유되지 않습니다.

초기에는 이를 허용하고, 필요할 경우 JSON Export / Import 방식의 백업 기능을 추가할 수 있습니다.

## 향후 회원 기능 추가 시

향후 로그인과 서버 동기화를 추가하더라도, 사용자가 매일 학습한 20개의 단어를 모두 영구 이벤트 Row로 저장하는 구조는 기본 설계로 사용하지 않습니다.

현재 학습 상태는 `회원 × 단어` 기준으로 관리하는 것을 고려합니다.

```text
Member
   │
   ▼
MemberWordProgress
   │
   ▼
Word
```

예:

```text
MemberWordProgress
├── memberId
├── wordId
├── status
├── correctCount
├── wrongCount
├── firstStudiedAt
├── lastStudiedAt
└── nextReviewAt
```

`(memberId, wordId)`를 유일한 조합으로 관리하면 같은 단어를 여러 번 학습하더라도 새로운 Row를 계속 추가하지 않고 기존 학습 상태를 갱신할 수 있습니다.

```text
처음 학습
→ INSERT

복습
→ UPDATE
```

따라서 데이터 증가 기준은 다음처럼 달라집니다.

```text
학습 이벤트 방식
회원 × 학습 횟수
→ 시간에 따라 계속 증가

학습 상태 방식
회원 × 실제 학습한 고유 단어
→ 단어 수를 기준으로 증가
```

## 학습 이력과 통계

상세 학습 이벤트가 반드시 필요한 것은 아닙니다.

초기에는 현재 상태만 저장하고, 통계 기능이 필요해질 때 별도의 이벤트 또는 집계 데이터를 추가합니다.

예를 들어 일별 통계는 20개의 상세 Row 대신 하나의 Summary로 저장할 수 있습니다.

```text
DailyStudySummary
├── memberId
├── studyDate
├── studiedCount
├── correctCount
└── completed
```

오래된 일별 데이터가 많아지면 월 단위로 집계하는 방식도 고려할 수 있습니다.

```text
DailyStudySummary
        │
        ▼
MonthlyStudySummary
```

상세 이벤트가 필요한 경우에도 이벤트를 무기한 RDB에 보관하기보다 일정 기간 이후 집계 또는 Archive하는 방향으로 확장합니다.

## 프로젝트 구조

초기 구조는 다음과 같은 형태를 고려합니다.

```text
jyp-word/
├── web/        # React 화면 및 IndexedDB 기반 사용자 학습 상태
├── api/        # Spring Boot 단어 조회 및 학습 콘텐츠 제공 API
├── data/       # 검수된 단어 원본 데이터
├── docs/       # 설계 문서
└── memory/     # 작업 상태와 장기 결정 기록
```

백엔드는 Java 21과 Spring Boot를 사용합니다.

프론트엔드는 초기 접근성과 배포 편의성을 우선해 React + TypeScript 기반 웹으로 구성하는 방향을 고려합니다.

웹 서비스로 제공하면 별도의 앱 설치 없이 휴대폰과 PC에서 같은 도메인으로 접근할 수 있으며, 필요하면 PWA 방식으로 확장할 수 있습니다.

## 도메인 구분

DDD 관점에서는 단어 자체와 사용자의 학습 과정을 분리하는 방향을 고려합니다.

```text
vocabulary
├── Word
├── Meaning
├── Example
└── Category

learning
├── DailyStudy
├── WordProgress
└── Review

member        # 회원 기능 추가 시
└── Member

auth          # 인증 기능 추가 시
├── Login
├── OAuth2
└── Token
```

초기에는 회원 기능이 없으므로 `member`, `auth`는 구현하지 않습니다.

향후 회원 기능을 도입한다면 다음처럼 책임을 분리합니다.

```text
Member
= 회원 정보와 회원 생명주기

Auth
= 로그인, OAuth2, 토큰 및 인증 과정
```

## 설계 원칙

### 학습 콘텐츠는 미리 준비합니다

단어를 보여줄 때마다 LLM이나 외부 사전을 호출하지 않습니다.

단어, 뜻, 발음, 예문, 예문 해석을 미리 준비하고 검수한 데이터를 사용해 동일한 입력에는 동일한 학습 콘텐츠가 제공되도록 합니다.

### 사용자 데이터는 필요한 상태만 저장합니다

과거의 모든 학습 행동을 무조건 저장하지 않습니다.

현재 학습에 필요한 상태를 우선 저장하고, 실제 제품 요구사항에 필요한 경우에만 이벤트와 통계를 추가합니다.

### 계산할 수 있는 데이터는 저장하지 않습니다

오늘의 20단어처럼 동일한 입력으로 다시 계산할 수 있는 값은 가능한 한 결정적으로 계산합니다.

이를 통해 사용자 수가 증가해도 불필요한 `회원 × 날짜 × 20단어` 형태의 데이터 증가를 줄입니다.

### 초기에는 Local-First로 시작합니다

회원가입 없이 IndexedDB에 학습 데이터를 저장해 서비스 구조를 단순하게 유지합니다.

기기 간 동기화가 실제 요구사항이 되는 시점에 회원과 서버 저장 기능을 추가합니다.

### 복잡도를 단계적으로 확장합니다

처음부터 완전한 개인화 학습 알고리즘을 만들지 않습니다.

```text
랜덤 20단어
   ↓
미학습 단어 우선
   ↓
틀린 단어 복습
   ↓
Spaced Repetition
   ↓
개인별 난이도 / 추천
```

처럼 실제 학습 데이터와 요구사항에 맞춰 단계적으로 발전시킵니다.

## 현재 결정된 방향

- 백엔드는 Java 21 + Spring Boot 사용
- 프론트엔드는 React + TypeScript 방향 우선 고려
- 초기에는 회원가입과 로그인 없음
- 사용자 학습 데이터는 IndexedDB에 저장
- 영단어 데이터는 런타임 생성이 아니라 사전 구축
- 난이도와 카테고리를 별도 기준으로 관리
- 하루 학습량은 기본 20단어
- 새로고침하더라도 같은 날에는 동일한 단어 세트를 제공하는 방향
- 향후 회원 기능 추가 시 `MemberWordProgress` 형태의 상태 기반 저장 고려
- 상세 학습 이벤트는 실제 통계 요구사항이 생길 때 추가

## 한계와 다음 단계

- 사용할 영단어 데이터셋과 데이터 라이선스는 아직 확정하지 않았습니다.
- 단어 데이터의 품질 검수 및 난이도 분류 기준이 필요합니다.
- 하루 20단어를 선정하는 정확한 알고리즘은 아직 확정하지 않았습니다.
- IndexedDB 스키마와 데이터 마이그레이션 정책을 정의해야 합니다.
- 복습 알고리즘과 `nextReviewAt` 계산 방식은 향후 설계 대상입니다.
- 회원 기능을 추가할 경우 Local 데이터와 서버 데이터의 동기화 정책이 필요합니다.
- 대규모 사용자 환경에서는 단어 풀 캐싱, 통계 집계, 데이터 보관 정책을 추가로 검토합니다.

앞으로는 우선 검수된 단어 데이터셋을 구성하고, 카테고리와 난이도를 기준으로 매일 20단어를 안정적으로 제공하는 최소 학습 흐름을 구현할 예정입니다.
